# 踩坑记录

按「会吃掉一整晚」的严重程度排序。每条都标了**怎么发现的**——比结论本身更有用。

---

## 1. 模块里绝对不能调 VFS（会挂死整机）

**症状**：模块 `insmod` 成功、`lsmod` 能看到，但只要 `cat /dev/tunsvc` 或
`echo > /dev/tunentry`，整机立刻无响应（模拟器上表现为 Studio 返回 HTTP 503）。

**原因**：为了做「有 `/data/tundebug` 才输出日志」，在 `svc_open()` / `entry_open()`
里调了 `stat("/data/tundebug")`。**在文件操作回调里做文件操作 = 重入 VFS**，直接死锁。

**怎么发现的**：模拟器 A/B —— 把那次 `stat` 换成常数，同样操作不再挂；
而且整个 3.5 KB 的完整页被编译器当死代码删掉（模块从 74,944 → 60,440 字节），
变量隔离得干干净净。

**那次 A/B 还有一个意外收获**：换了常数后模块变小 1.4 万字节，说明**完整诊断页占了模块
近 20% 的体积**——它本来就不该默认开着。

**结论**：
- 模块内部**不碰文件系统**，任何时机都不碰（open / read / write 三条路径都试过，全挂）。
- 「有没有某个文件」这种判断放到**用户态**（nsh 的 `[ -f ]`）做，模块只收一条命令（97/98）。

> ⚠️ 反例警告：另一个模块（capatch）在真机 `write` 里调 `stat` 曾经成功返回
> `st_mode=0x8180`。**那是运气，不是证据**。不要拿它当"VFS 可调"的先例。

## 2. nsh 的 `cat 文件 > /dev/xxx` 是 4 字节步长散开的

下发命令必须用 `echo 3 > /dev/tunentry`，**不能**用 `cat cmds.txt > /dev/tunentry`。

v74 的实测现场（模块自己记的）：

```
entry_head = 6d 00 00 00 74 00 00 00     ⇒ 'm'@0、't'@4，不是连续的 "mt_cmd=18"
```

`echo` 是逐字节 write（`write("1")`、`write("6")`、`write("\n")`），流式解析器能接住；
`cat` 那条路会带零填充，永远拼不齐 ⇒ 命令全被拒（`entry_bad` 涨）。

## 3. 写命令只是入队，必须读一次节点才执行

```c
if(c == 3u) { ... mt_stage_arm(); }    /* 在 mt_cmd_poll() 里 */
```

`mt_cmd_poll()` 的调用点只有三处：`svc_read`（读 `/dev/tunsvc`）、`stat_read`
（读 `/dev/tunentry`）、周期服务。所以：

- `echo 3 > /dev/tunentry` 之后**不读节点** ⇒ 命令永远躺在 `g_mt_cmd` 里
- 自启脚本每条 `echo` 后面都跟一个 `cat /dev/tunsvc > armN.txt`，就是为了触发 + 留证

## 4. 改资源布局长度，所有校验都要跟着改（同一个坑踩了两次）

资源槽位是四段拼接：

```
[tun 74640][CA 223684][capatch 8060][ca.pem 4038]   = 310422
```

第一次踩：加了 capatch + ca.pem 两段，但**忘记改总长校验**
（`#raw ~= MODULE_SIZE + CA_SIZE`），真机按钮①直接 `resource read failed`。

第二次踩：重新编模块后 `MODULE_SIZE` 从 75112 变成 74640，偏移又是写死的字面量。

**现在的做法**：

```lua
local CAP_OFF = MODULE_SIZE + CA_SIZE        -- 推导，不写字面量
local PEM_OFF = CAP_OFF + CAP_SIZE
local RES_TOTAL = MODULE_SIZE + CA_SIZE + CAP_SIZE + PEM_SIZE
```

打包门（`pack_mwz.py`）用**同一套算法**独立推一遍再比对——两边算错才会同时错。

## 5. `MT_BUILD` 必须随模块一起变

表盘按①时读 `/dev/tunentry` 的 `mt_build` 和资源里的模块比对，不一致就拒绝：

> 模块文件已写好，但内存里跑的还不是这一版（读到 v107…，应为 v108…）。请重启手表，再按一次①

改了模块却忘了改 `MT_BUILD`，等于**版本校验形同虚设**（新旧模块 build 串一样，永远通过）。
所以：**动模块代码 ⇒ 同时改 `mpu_trap.h` 的 `MT_BUILD` 和表盘的 `MODULE_BUILD`**。

## 6. 布防必须 1→2→3→4，缺一步 DNS 就不生效

```
1 双向量 + MEMFAULTENA → 2 MPU + 预检 → 3 布防解析器窗口 → 4 替换路径验证
```

**3 才是 DNS 开始生效的那一步**。曾经把「分级布防」当调试按钮删掉，结果 DNS 立刻挂
（手机侧抓包：完全没有 UDP/53，只有一条 `dest_ip/80` 的 TCP）。

现在表盘把布防并进了按钮①，一次跑完四步。

---

## 7. 模拟器不能否掉布防（QEMU 不支持 MPU/向量操作）

布防 1..4 在 QEMU 里会挂死（vmpu/向量表那些地址在模拟器上没有真实语义）。
**这不能说明真机也挂** —— 真机上布防是反复验证过的。

判据分工：

| 问题 | 在哪判 |
|---|---|
| 短页/完整页、命令流、日志开关、资源长度 | 模拟器（可靠）|
| 布防、netdev 注册、DHCP、DNS 实际收发 | **只能真机** |

## 8. 别把「测试卡」当长期表盘

表盘一旦是当前表盘，**每次开机都会自动跑一次**。曾经有一版测试卡在构造函数里做
「有副作用」的初始化（自己 malloc 建 CA 链），结果每次开机都重新施加一遍，
表现成「重启也修不好」。

规矩：
- 测试卡只在按下按钮后才做事，**加载时零副作用**
- 会改全局状态的卡，必须配一张**长期驻留也无副作用**的回滚卡
- 排查"重启能不能恢复"之前，先确认**没有自启动的东西在重复施加影响**

## 9. 判据必须能 FAIL（验证自己的验证）

写离线门时最容易骗自己的是「判据写松了，改了代码照样绿」。

做法：**每次加判据，都把被测代码改回错误状态跑一次，必须 FAIL**。

例子：把自启脚本首行 `# top1` 改成 `# TOP1`，`A1/A2` 立刻红；改回来就绿。
这一步只花一分钟，但它决定了那些绿勾到底有没有意义。

## 10. 杂项

- **adb over WiFi**：端口不是 5555。`adb connect <ip>:<port>`；`adb pull` 必须
  `MSYS_NO_PATHCONV=1`，否则 Git Bash 会把设备路径改成本机路径。
- **`md5 -f <path>`**：设备上的 `md5` 不带 `-f` 算的是**参数字符串本身**的哈希，
  校验文件必须带 `-f`。
- **模拟器实例重启后端口会变**（QMP/GDB），工具里写死端口的脚本要跟着改。
